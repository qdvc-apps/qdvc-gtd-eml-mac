I'll start by studying the existing repositories to understand the conventions and the GTD tool itself.I've cloned all five repositories and read the GTD tool's Python modules, its MAINTENANCE guide, and the single-page app's sidebar, toolbar and action definitions. Before writing any Swift, a few decisions affect the architecture, so I've put together a design proposal for you to react to. The mockup above shows the proposed window.

### The proposal in brief

The app follows the same approach as the Nice Mail and Bibliotheca ports. The Python core is rewritten in Swift as a Foundation-only `GTDCore` module, with parity fixtures generated from the Python code. On top of that sits a SwiftUI/AppKit front-end. It has no Xcode project, and `scripts/build-app.sh` produces an ad-hoc-signed bundle. The workspace stays the contract, so the CLI and the app can take turns on the same folder, and every refusal the CLI makes is enforced here too.

The window is a Mail-style three-pane `NavigationSplitView`. The sidebar has four sections, relabelled in Mail's vocabulary:

- **Overview:** Dashboard and Performance.
- **Workflow:** the six folders, with counts.
- **Smart Mailboxes:** due date, pinned, and one per hashtag.
- **Accounts:** Inbox and Sent for each of your own accounts.

The message list uses Mail-like rows. The age dot sits where Mail puts its unread dot, and the next action is the preview line.

The reading pane leads with an editable annotations card, followed by the workflow trail and then the collapsible message history. That is the same order as the web UI.

The CLI actions map onto Mail's own commands wherever Mail has one:

- **Ingest** is "Get Mail" (⇧⌘N).
- **`alloc`** is Move To (⌃⌘1–6), or dragging a message onto a sidebar folder.
- **`alloc archive`** is Archive (⌃⌘A).
- **Pin** is Flag (⇧⌘L).
- **`workflow_autofix`** becomes a review sheet that lists every proposed stamp and has a single Apply button, reached from a banner when fixes are outstanding.

There's no undo for moves, because undoing one would mean clearing a `ds_*` stamp, which the CLI never allows. Instead, a move the CLI would refuse is disabled, and its help tag gives the reason.

The full detail, including the module plan and the parity-testing strategy, is in `docs/DESIGN.md` in the ZIP.

### Questions before I start

1. **Where should settings come from?** This is the one I most need your answer on. The CLI reads `config.yml` from beside its own code, not from the workspace. So pointing the app at a workspace doesn't reveal `my_own_accounts`, `monitored_hashtags`, the age thresholds, or `max_filename_chars`, and that last one changes the filenames ingest produces. The options are:
   - (a) The app's own Settings, stored per workspace.
   - (b) You point the app at your `config.yml` once, and it reads it (read-only).
   - (c) Both, with `config.yml` winning when chosen.

   I'd lean towards (c), so the two tools never disagree about filenames.
2. **Is the action scope right?** I've proposed ingest, alloc, close, pin/unpin, metadata editing, workflow autofix and metadata check. I'd leave out `generate_dashboard` and `export`, since the app is itself the dashboard.
3. **Should Performance be in the first version, or a later phase?** Swift Charts handles the box plots, bars and throughput lines well. It has no Sankey, though, so that would be hand-drawn. I'd suggest shipping the mail interface and actions first.
4. **Should ingest happen automatically?** `gtd list` ingests on every run. I'd suggest ingesting only on the explicit Ingest command, with an opt-in setting to ingest on open and on Refresh. Mutating the workspace just by opening it feels un-Mac-like.
5. **Are these names OK?** Repository `qdvc-gtd-eml-mac`, app "QDVC GTD EML", bundle id `org.qdvc.GTDEML`.

One practical note: there's no Swift toolchain available in my environment. I'll write the code carefully and review it by hand, but the first `swift build` and `swift test` on your Mac will be its first compile, so expect a round of small fixes.
